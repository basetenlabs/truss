# Cannery CLI machine protocol v1

`cannery_cli_v1.proto` and this document are the normative v1 contract. The
Protobuf file defines the binary data shape and the ProtoJSON mapping used for
bootstrap and decoded debug artifacts. This document defines argv, framing,
ordering, exit, cancellation, compatibility, and security behavior that
Protobuf cannot express.

The public `cannery` binary implements this contract using the generated Rust
types from this crate.

## Bootstrap discovery

Before starting an operation, a wrapper runs:

```text
cannery protocol
```

The command is non-mutating: it performs no network requests and makes no
filesystem changes other than normal process startup. It writes exactly one
small JSON `ProtocolBootstrapV1` object followed by a newline to stdout and
exits `0`:

```json
{"bootstrap_version":1,"cannery_version":"1.2.3","supported_machine_protocols":[1],"supported_encodings":["protobuf-delimited","protojson-ndjson"]}
```

Bootstrap stderr is diagnostic text only. A bootstrap usage or internal error
exits nonzero and does not emit a partial JSON object. Wrappers parse only this
envelope and select a mutually supported protocol before launching an
operation.

`protobuf-delimited` is the required production v1 encoding.
`protojson-ndjson` is optional and indicates that the executable also supports
explicit local debug output. Production wrappers require and explicitly select
`protobuf-delimited`; they never fall back to the debug encoding. The
bootstrap remains JSON so the wrapper can negotiate before it opens a binary
operation stream.

## Invocation and request mapping

Machine protocol v1 is selected explicitly:

```text
cannery --machine-protocol 1 --machine-encoding protobuf-delimited push PATH REF [--max-bytes-in-flight BYTES] [--max-concurrency COUNT]
cannery --machine-protocol 1 --machine-encoding protobuf-delimited ls [NAMESPACE_OR_REF] [--all] [--page-size SIZE] [--page-token TOKEN]
cannery --machine-protocol 1 --machine-encoding protobuf-delimited show REF [--page-size SIZE] [--page-token TOKEN]
cannery --machine-protocol 1 --machine-encoding protobuf-delimited pull REF OUT_DIR [--include PATH]... [--restart] [--max-bytes-in-flight BYTES] [--max-concurrency COUNT]
```

The `CommandRequestV1` variants mirror the parsed argv values. They do not
introduce a second request transport. Local source and destination paths remain
platform-native strings; references and namespace selectors use Cannery's CLI
grammar. Push requires an explicit destination reference. Pull include paths
are normalized portable volume-relative strings as defined below. Merge,
overwrite, and discard modes are not public v1 argv.

Credential values must be supplied through the separately defined credential
channel. They must never appear in argv, requests, records, stderr, or
diagnostic logs.

`--machine-encoding` is required with `--machine-protocol`. An unsupported
protocol version or encoding fails before network or operation filesystem
mutations and emits no partial machine frame.

## Production binary stream

Production stdout contains repeated
`MachineRecordV1.encode_length_delimited` output. Each frame is:

```text
canonical unsigned varint payload_length | payload_length Protobuf bytes
```

`MAX_MACHINE_FRAME_BYTES_V1` is 8,388,608 bytes (8 MiB), excluding the length
prefix. Producers must not emit a larger payload. Consumers enforce the bound
before allocating or reading a payload body.

### Framing and incremental reads

The length prefix is the shortest canonical unsigned base-128 Protobuf varint.
Since the maximum accepted length is 8 MiB, a valid prefix is at most four
bytes. A consumer:

1. Reads the prefix one byte at a time, with no speculative body allocation.
2. Rejects a continuation bit on prefix byte four, any longer or non-minimal
   representation, and any decoded value above 8,388,608.
3. Rejects length zero; an empty `MachineRecordV1` is never a keepalive or EOF
   marker.
4. Reads exactly the declared number of payload bytes into a buffer no larger
   than the frame cap.
5. Decodes and processes that record before reading the next frame, reusing or
   releasing the bounded buffer and not retaining unbounded progress history.

EOF before any byte of a new prefix is clean framing EOF. EOF after one or more
prefix bytes is a truncated-prefix failure. EOF after a complete prefix but
before all declared payload bytes is a truncated-frame failure. A nonzero body
that decodes to the default record, has no known payload, or otherwise fails
the record invariants below is not an empty-stream marker; it is a protocol
failure.

For an accepted operation invocation, clean framing EOF is semantically valid
only after exactly one terminal record. EOF before the first frame is a
missing-started protocol failure. The sole empty-stdout exception is process
exit `2` for pre-stream syntax, flag, protocol, or encoding validation; the
wrapper reports a usage/invocation failure and does not treat it as a machine
session. EOF after `started` or an intermediate record is a missing-terminal
failure. After a terminal record, a consumer reads once more: immediate EOF is
required, and any byte is a records-after-terminal failure even if it is only a
partial prefix.

Human text, JSON, ANSI control sequences, and tracing output are forbidden on
production stdout. Stderr is outside the machine protocol. It is reserved for
last-resort launch, runtime, stream, and crash diagnostics when a valid record
cannot be emitted. Wrappers capture and redact stderr; they never parse it as
records.

Each frame is flushed after its prefix and payload are written. Serialization,
prefix-write, body-write, and flush failures are fatal machine-stream failures.
On `EPIPE` or an equivalent broken stdout, Cannery marks stdout unusable, stops
scheduling work, cancels active operation futures, drops in-memory credential
state, releases process-lifetime locks, and does not attempt to write a
terminal record to the broken stream. It exits `1` unless an already-observed
user cancellation owns exit `130`. A mutation completed before the failed
write cannot be undone, but Cannery schedules no new operation work after
detecting the broken pipe and never treats the failed frame as delivered.

Every record has:

- `protocolVersion`: exactly `1`.
- `sequence`: starts at `1` and increases by one with no duplicates.
- `operationId`: one nonempty opaque identifier shared by the operation.
- `operation`: exactly `OPERATION_PUSH`, `OPERATION_LIST`, `OPERATION_SHOW`, or
  `OPERATION_PULL`, matching the request.
- exactly one payload.

The `*_UNSPECIFIED` zero values are reserved for Protobuf construction and are
invalid on the wire. Binary enum fields carry numbers. Generated consumers
retain an unknown enum number during parsing and reserialization, but an
unknown value in a field whose meaning controls operation, result, error, or
terminal handling is an unsupported semantic and fails loudly.

The first record is `started`, containing the parsed `CommandRequestV1`. Zero
or more `progress`, `status`, and `warning` records follow. Exactly one terminal
record follows: `result`, `error`, or `cancelled`. No record may follow the
terminal record. A `result` variant must match `operation`.

Progress is emitted on a bounded cadence rather than once per chunk. Consumers
process it incrementally and must not retain an unbounded operation history.
Counters are cumulative within an operation and never decrease. Totals may be
absent until known.

Stable launch-vertical progress phases are:

- push: `scan`, `hash`, `upload`, `commit`
- list: `list`
- show: `resolve`, `inspect`
- pull: `resolve`, `validate`, `download`, `verify`, `publish`

Status and warning `reason` values are stable `UPPER_SNAKE_CASE` identifiers;
their messages are human-readable and may change.

## Debug encoding and decoder

An executable may advertise `protojson-ndjson` and accept it only when selected
explicitly:

```text
cannery --machine-protocol 1 --machine-encoding protojson-ndjson OPERATION ...
```

Debug stdout contains one standard ProtoJSON `MachineRecordV1` and `\n` per
record. The maximum encoded line, excluding `\n`, is also 8,388,608 bytes.
Record ordering, terminal, exit, cancellation, and redaction rules are
identical to the production encoding. This mode exists for local producer or
consumer development where readable live stdout matters. Truss and other
production wrappers must not select it, release compatibility tests must not
substitute it for binary coverage, and production artifact pins always name
`protobuf-delimited`.

The supported production-stream decoder is:

```text
cannery protocol decode [FILE|-]
```

An omitted file or `-` reads framed bytes from stdin. The decoder performs the
same prefix, size, Protobuf, sequence, terminal, and EOF validation as a
wrapper. It writes one canonical ProtoJSON object per complete frame and writes
redacted human diagnostics to stderr. Canonical decoder output is UTF-8 with
lowerCamelCase field names, symbolic known enum names, decimal strings for
64-bit integers, decimal JSON numbers for unknown enum values,
lexicographically ordered keys, no insignificant whitespace, and one trailing
newline per record.

Checked ProtoJSON NDJSON fixtures are decoder-produced review artifacts. Binary
goldens remain authoritative for exact framing, partial-read, unknown-field,
and unknown-enum behavior. ProtoJSON cannot represent unknown fields that the
decoder's schema does not name, so decoded output is not a byte-lossless
replacement for the framed fixture. Use the decoder for captured production
streams, fixture updates, compatibility investigations, and support
reproduction; use direct JSON debug mode only for local live-stream
development.

## Results

`PushResultV1` reports immutable content identity, the canonical resolvable
reference, creation/tag outcomes, snapshot sequence, and transfer counters.

`ListResultV1` is either a namespace page or a reference page. Reference
entries use `REFERENCE_ENTRY_KIND_TAG` or
`REFERENCE_ENTRY_KIND_IMMUTABLE_DIGEST`; consumers do not infer the kind by
parsing display text. `nextPageToken` is absent on the final page.

`ShowResultV1` reports resolved metadata and one `FilePageV1`. File entries use
`FILE_ENTRY_KIND_FILE`, `FILE_ENTRY_KIND_DIRECTORY`, or
`FILE_ENTRY_KIND_SYMLINK`. A `backingObjectDigest` identifies the backing
object and must not be described as a whole-file content digest unless it
actually is one. Every successful show includes `filePage`, including an empty
final page.

`PullResultV1` reports the selected graph. `logicalBytes`, `fileCount`, and
`directoryCount` therefore describe only entries extracted by this invocation.
For a subset pull, `volumeLogicalBytes`, `volumeFileCount`, and
`volumeDirectoryCount` report the corresponding totals from the complete
validated manifest. They are absent for a complete pull. `contentVerified` is
true before a successful result is emitted.

### Pull include selectors

`--include PATH` is repeatable. No include selector means the complete volume.
Selectors never use glob syntax. Multiple selectors form a union and duplicate
matches are extracted once.

Each selector is a UTF-8, forward-slash-separated path relative to the volume
root. A single trailing slash is accepted and removed before the request is
recorded. Empty paths, absolute paths, drive-prefixed paths, backslashes, NUL
bytes, `.` or `..` components, and empty or otherwise ambiguous components are
invalid. Validation is lexical and platform-independent.

A selector that names a file or symlink selects exactly that entry. A selector
that names a directory selects that directory and all descendants; descendant
matching uses a `/` boundary, so `tokenizer` never selects `tokenizer-old`.
Only directories required as parents of selected files, symlinks, or selected
directories are included. Unselected sibling entries are not included.

The complete untrusted manifest is validated before selector filtering. Pull
does not follow symlinks while matching or extracting. After manifest
validation and filtering, but before staging or any chunk or chunkmap fetch,
the operation fails with `INVALID_ARGUMENT` / `INCLUDE_PATH_NOT_FOUND` if the
selectors match no extractable file or symlink. Selecting only an explicit
empty directory therefore fails.

### Pull resume

Pull staging is keyed by the resolved manifest digest, canonical absolute
destination, and normalized selector set. Selector order and duplicates do not
change that identity, while a different selector set or moved tag cannot reuse
staged content. Before reuse, each checkpointed range is rehashed against its
expected digest.

`--restart` discards only the resumable state matching that complete identity
and starts the pull again. It does not discard state for another manifest,
destination, or selector set.

List and show default to 100 entries per page and enforce a hard maximum of
1,000 entries per page. `pageSize` above 1,000 is `invalid_argument`; zero or
an absent value selects the default. `pageToken` is opaque and scoped to the
unchanged request. `nextPageToken` is absent on the final page. Each show
invocation returns at most one bounded file page; callers retrieve another
page with a new invocation. Encoding is not a reason to accumulate unbounded
metadata.

## Errors

`category` is a Protobuf enum and `reason` is a stable string. `message` is
human-readable. Context belongs in `message` or typed `details` and is never
prepended to `reason`.

The closed v1 category set is:

- `ERROR_CATEGORY_INVALID_ARGUMENT`
- `ERROR_CATEGORY_AUTHENTICATION`
- `ERROR_CATEGORY_AUTHORIZATION`
- `ERROR_CATEGORY_NOT_FOUND`
- `ERROR_CATEGORY_CONFLICT`
- `ERROR_CATEGORY_THROTTLED`
- `ERROR_CATEGORY_QUOTA`
- `ERROR_CATEGORY_UNAVAILABLE`
- `ERROR_CATEGORY_INTEGRITY`
- `ERROR_CATEGORY_UNSUPPORTED_PROTOCOL`
- `ERROR_CATEGORY_INTERNAL`

An error uses the matching `ErrorDetailsV1` variant when that category has one.
`internal` has no typed detail because internal context must not cross the
security boundary. `retryable` states whether retrying without changing the
request may succeed. A server-provided retry delay is preserved in
`retryAfterMs` without rounding away sub-second precision; it is absent when
unknown. `ERROR_CATEGORY_THROTTLED` and `ERROR_CATEGORY_UNAVAILABLE` may be
retryable. `ERROR_CATEGORY_QUOTA` is not retryable unless the server explicitly
reports that the quota is transient.

Unknown categories or reasons are not silently reclassified by wrappers. A
binary parser retains an unknown `ErrorCategory` numeric value, but because the
category controls wrapper behavior, the wrapper reports unsupported protocol
semantics rather than mapping it to `internal`, success, or retry. Unknown
reason strings are handled the same way while preserving a redacted message.
Retaining an enum number makes the wire parseable; it does not make the new
meaning safe for an older consumer.

## Cancellation and exit codes

On SIGINT or SIGTERM, Cannery drops the operation future, aborts its active
transfer tasks, drops in-memory credential state, and releases process-lifetime
locks before emitting `cancelled` if stdout remains writable. Pull staging is
intentionally retained for resume, so `cleanupCompleted` remains true without
destructive staging cleanup. A cancelled operation never emits `result` or
`error`.

Exit meanings are:

- `0`: a terminal `result` was emitted.
- `1`: a terminal `error` was emitted, or a machine-stream write failure made
  terminal delivery impossible.
- `2`: invalid command syntax, flag, selector, or reference prevented a v1
  stream from starting.
- `130`: user cancellation; a `cancelled` record is emitted when possible.

A wrapper also treats a platform-equivalent interrupt status as cancellation
when the process could not emit a terminal record. Empty streams, malformed or
oversized varints, truncated frames, zero-length frames, malformed Protobuf,
sequence gaps, metadata mismatches, records after terminal, and exit/terminal
mismatches are protocol failures and must fail loudly.

## Compatibility

Within v1, existing field numbers, variants, types, meanings, argv semantics,
stream ownership, framing, ordering, and exit meanings cannot change. Fields
and enum values cannot be removed, renumbered, or repurposed.

Binary Protobuf supplies normal additive-field behavior: an older consumer
ignores field numbers it does not know instead of rejecting the record.
Generated consumers also retain unknown enum numeric values during parsing and
reserialization. A new optional field is wire-compatible only when its absence
preserves the complete old behavior; a producer cannot make the field required
for correctness merely because the bytes are parseable.

Binary compatibility is not semantic compatibility. An older wrapper must fail
loudly when an unknown enum value or missing known oneof prevents it from
interpreting operation, result, error, cancellation, or terminal behavior. New
required behavior, new terminal meanings, incompatible command semantics, and
record variants that old consumers cannot safely ignore require an advertised
capability or a new machine protocol version. Old and new protocol versions are
supported concurrently for a documented migration window.

Exact wrapper artifact pins, bootstrap protocol/encoding negotiation, and an
exact generated-schema input remain required. Schema changes run Buf lint, Buf
breaking checks, generated Rust/Python drift checks, binary golden and
partial-read tests, canonical decoded ProtoJSON fixture tests, decoder
equivalence, and producer/consumer compatibility. The checked-in generated
files are derived artifacts, not a second schema.

## Security and redaction

Records may contain customer references and local paths but never bearer
tokens, API keys, signed URLs, credential-file contents, request headers, or
raw internal error chains. Human messages and typed details follow the same
rule. Wrappers redact captured stderr before persistence or display.
