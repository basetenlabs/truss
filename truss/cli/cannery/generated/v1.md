# Cannery CLI machine protocol v1

`cannery_cli_v1.proto` and this document are the normative v1 contract. The
Protobuf file defines data shape and ProtoJSON mapping. This document defines
argv, stream, ordering, exit, cancellation, compatibility, and security
behavior that Protobuf cannot express.

The public `cannery` binary implements this contract using the generated Rust
types from this crate.

## Bootstrap discovery

Before starting an operation, a wrapper runs:

```text
cannery protocol
```

The command is non-mutating: it performs no network requests and makes no
filesystem changes other than normal process startup. It writes exactly one
ProtoJSON `ProtocolBootstrapV1` object followed by a newline to stdout and
exits `0`:

```json
{"bootstrap_version":1,"cannery_version":"1.2.3","supported_machine_protocols":[1],"supported_encodings":["protojson-ndjson"]}
```

Bootstrap stderr is diagnostic text only. A bootstrap usage or internal error
exits nonzero and does not emit a partial JSON object. Wrappers parse only this
envelope and select a mutually supported protocol before launching an
operation.

`protojson-ndjson` is the only required v1 encoding. The schema reserves
`protobuf-delimited` for a future length-delimited binary encoding. Advertising
or selecting that encoding later does not change v1 semantics.

## Invocation and request mapping

Machine protocol v1 is selected explicitly:

```text
cannery --machine-protocol 1 push PATH REF [--max-bytes-in-flight BYTES] [--max-concurrency COUNT]
cannery --machine-protocol 1 ls [NAMESPACE_OR_REF] [--all] [--page-size SIZE] [--page-token TOKEN]
cannery --machine-protocol 1 show REF [--page-size SIZE] [--page-token TOKEN]
cannery --machine-protocol 1 pull REF OUT_DIR [--include PATH]... [--restart] [--max-bytes-in-flight BYTES] [--max-concurrency COUNT]
```

The `CommandRequestV1` variants mirror the parsed argv values. They do not
introduce a second request transport. Local source and destination paths remain
platform-native strings; references and namespace selectors use Cannery's CLI
grammar. Push requires an explicit destination reference. Pull include paths
are normalized portable volume-relative strings as defined below. Merge,
overwrite, and discard modes are not public v1 argv.

Credential values must be supplied through the separately defined credential
channel. They must never appear in argv, requests, records, stderr, or
diagnostic logs.

An unsupported protocol version fails before network or operation filesystem
mutations.

## ProtoJSON NDJSON stream

Stdout contains one standard ProtoJSON `MachineRecordV1` per line. Every line
is a complete JSON object terminated by `\n`. Human text, ANSI control
sequences, and tracing output are forbidden on stdout.

ProtoJSON's normal lowerCamelCase field names apply. Its 64-bit integer mapping
also applies: `sequence`, byte counters, file counters, and other `uint64`
values are decimal JSON strings. Consumers may accept alternate spellings that
the ProtoJSON specification permits, but producers emit canonical field names
and string-encoded 64-bit integers.

Stderr is outside the machine protocol. It is reserved for last-resort launch,
runtime, and crash diagnostics when a valid record cannot be emitted. Wrappers
capture and redact stderr; they never parse it as records.

Serialization, write, newline, and flush failures are fatal machine-stream
failures. Once the consumer is gone, Cannery stops scheduling operation work,
does not perform a later mutation, and terminates after dropping operation
state. It never treats a failed record write as if the record was delivered.

Every record has:

- `protocolVersion`: exactly `1`.
- `sequence`: starts at `"1"` and increases by one with no duplicates.
- `operationId`: one nonempty opaque identifier shared by the operation.
- `operation`: exactly `OPERATION_PUSH`, `OPERATION_LIST`, `OPERATION_SHOW`, or
  `OPERATION_PULL`, matching the request.
- exactly one payload.

The `*_UNSPECIFIED` zero values are reserved for Protobuf construction and are
invalid on the wire. Producers emit the exact prefixed symbolic enum names
shown in this document, never integer enum values.

The first record is `started`, containing the parsed `CommandRequestV1`. Zero
or more `progress`, `status`, and `warning` records follow. Exactly one terminal
record follows: `result`, `error`, or `cancelled`. No record may follow the
terminal record. A `result` variant must match `operation`.

Progress is emitted on a bounded cadence rather than once per chunk. Consumers
process it incrementally and must not retain an unbounded operation history.
Counters are cumulative within an operation and never decrease. Totals may be
absent until known.

Stable launch-vertical progress phases are:

- push: `scan`, `hash`, `upload`, `commit`
- list: `list`
- show: `resolve`, `inspect`
- pull: `resolve`, `validate`, `download`, `verify`, `publish`

Status and warning `reason` values are stable `UPPER_SNAKE_CASE` identifiers;
their messages are human-readable and may change.

## Results

`PushResultV1` reports immutable content identity, the canonical resolvable
reference, creation/tag outcomes, snapshot sequence, and transfer counters.

`ListResultV1` is either a namespace page or a reference page. Reference
entries use `REFERENCE_ENTRY_KIND_TAG` or
`REFERENCE_ENTRY_KIND_IMMUTABLE_DIGEST`; consumers do not infer the kind by
parsing display text. `nextPageToken` is absent on the final page.

`ShowResultV1` reports resolved metadata and one `FilePageV1`. File entries use
`FILE_ENTRY_KIND_FILE`, `FILE_ENTRY_KIND_DIRECTORY`, or
`FILE_ENTRY_KIND_SYMLINK`. A `backingObjectDigest` identifies the backing
object and must not be described as a whole-file content digest unless it
actually is one. Every successful show includes `filePage`, including an empty
final page.

`PullResultV1` reports the selected graph. `logicalBytes`, `fileCount`, and
`directoryCount` therefore describe only entries extracted by this invocation.
For a subset pull, `volumeLogicalBytes`, `volumeFileCount`, and
`volumeDirectoryCount` report the corresponding totals from the complete
validated manifest. They are absent for a complete pull. `contentVerified` is
true before a successful result is emitted.

### Pull include selectors

`--include PATH` is repeatable. No include selector means the complete volume.
Selectors never use glob syntax. Multiple selectors form a union and duplicate
matches are extracted once.

Each selector is a UTF-8, forward-slash-separated path relative to the volume
root. A single trailing slash is accepted and removed before the request is
recorded. Empty paths, absolute paths, drive-prefixed paths, backslashes, NUL
bytes, `.` or `..` components, and empty or otherwise ambiguous components are
invalid. Validation is lexical and platform-independent.

A selector that names a file or symlink selects exactly that entry. A selector
that names a directory selects that directory and all descendants; descendant
matching uses a `/` boundary, so `tokenizer` never selects `tokenizer-old`.
Only directories required as parents of selected files, symlinks, or selected
directories are included. Unselected sibling entries are not included.

The complete untrusted manifest is validated before selector filtering. Pull
does not follow symlinks while matching or extracting. After manifest
validation and filtering, but before staging or any chunk or chunkmap fetch,
the operation fails with `INVALID_ARGUMENT` / `INCLUDE_PATH_NOT_FOUND` if the
selectors match no extractable file or symlink. Selecting only an explicit
empty directory therefore fails.

### Pull resume

Pull staging is keyed by the resolved manifest digest, canonical absolute
destination, and normalized selector set. Selector order and duplicates do not
change that identity, while a different selector set or moved tag cannot reuse
staged content. Before reuse, each checkpointed range is rehashed against its
expected digest.

`--restart` discards only the resumable state matching that complete identity
and starts the pull again. It does not discard state for another manifest,
destination, or selector set.

List and show default to 100 entries per page and enforce a hard maximum of
1,000 entries per page. `pageSize` above 1,000 is `invalid_argument`; zero or
an absent value selects the default. `pageToken` is opaque and scoped to the
unchanged request. `nextPageToken` is absent on the final page. Each show
invocation returns at most one bounded file page; callers retrieve another
page with a new invocation. Encoding is not a reason to accumulate unbounded
metadata.

## Errors

`category` is a Protobuf enum and `reason` is a stable string. `message` is
human-readable. Context belongs in `message` or typed `details` and is never
prepended to `reason`.

The closed v1 category set is:

- `ERROR_CATEGORY_INVALID_ARGUMENT`
- `ERROR_CATEGORY_AUTHENTICATION`
- `ERROR_CATEGORY_AUTHORIZATION`
- `ERROR_CATEGORY_NOT_FOUND`
- `ERROR_CATEGORY_CONFLICT`
- `ERROR_CATEGORY_THROTTLED`
- `ERROR_CATEGORY_QUOTA`
- `ERROR_CATEGORY_UNAVAILABLE`
- `ERROR_CATEGORY_INTEGRITY`
- `ERROR_CATEGORY_UNSUPPORTED_PROTOCOL`
- `ERROR_CATEGORY_INTERNAL`

An error uses the matching `ErrorDetailsV1` variant when that category has one.
`internal` has no typed detail because internal context must not cross the
security boundary. `retryable` states whether retrying without changing the
request may succeed. A server-provided retry delay is preserved in
`retryAfterMs` without rounding away sub-second precision; it is absent when
unknown. `ERROR_CATEGORY_THROTTLED` and `ERROR_CATEGORY_UNAVAILABLE` may be
retryable. `ERROR_CATEGORY_QUOTA` is not retryable unless the server explicitly
reports that the quota is transient.

Unknown categories or reasons are not silently reclassified by wrappers.
Unknown ProtoJSON enum names and numeric values are rejected by the generated
v1 parsers. Because ProtoJSON has no binary Protobuf unknown-enum preservation,
new enum values require coordinated consumer support before a producer emits
them; otherwise they require a new machine protocol version. Unknown reason
strings surface as unsupported protocol values while preserving a redacted
message.

## Cancellation and exit codes

On SIGINT or SIGTERM, Cannery drops the operation future, aborts its active
transfer tasks, drops in-memory credential state, and releases process-lifetime
locks before emitting `cancelled` if stdout remains writable. Pull staging is
intentionally retained for resume, so `cleanupCompleted` remains true without
destructive staging cleanup. A cancelled operation never emits `result` or
`error`.

Exit meanings are:

- `0`: a terminal `result` was emitted.
- `1`: a terminal `error` was emitted.
- `2`: invalid command syntax, flag, selector, or reference prevented a v1
  stream from starting.
- `130`: user cancellation; a `cancelled` record is emitted when possible.

A wrapper also treats a platform-equivalent interrupt status as cancellation
when the process could not emit a terminal record. EOF, malformed JSON,
sequence gaps, metadata mismatches, and exit/terminal mismatches are protocol
failures and must fail loudly.

## Compatibility

Within v1, existing fields, variants, types, meanings, argv semantics, stream
ownership, ordering, and exit meanings cannot change. Enum values cannot be
removed, renumbered, or repurposed. New enum values are schema-additive but
cannot be emitted until every supported ProtoJSON consumer recognizes them.
New optional fields may be added. New record variants require an explicit v1
rule that old consumers can safely ignore them; no such extension is currently
allowed.

Standard ProtoJSON parsers reject unknown fields unless a consumer explicitly
enables its implementation's unknown-field option. Therefore a newly emitted
field is not wire-compatible until supported consumers have rolled out that
option or learned the field. Missing required behavioral fields, malformed
oneofs, unsupported protocol versions, and unknown terminal variants fail
loudly. A breaking change creates a new machine protocol version, supported
concurrently for a documented migration window.

Schema changes run Buf lint, generated-code drift, ProtoJSON fixture, and Buf
breaking checks. The checked-in generated Rust files are derived artifacts, not
a second schema.

## Security and redaction

Records may contain customer references and local paths but never bearer
tokens, API keys, signed URLs, credential-file contents, request headers, or
raw internal error chains. Human messages and typed details follow the same
rule. Wrappers redact captured stderr before persistence or display.
